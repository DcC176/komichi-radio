# 二十四时小路电台

四时小路Komichi 直播回放的 24 小时频道（非官方粉丝向站点）。打开网页即进入「正在直播中」的状态，
自动排期、自动去重，无需任何服务端。

---

## 快速开始

**方式一：双击 `启动.bat`**

首次运行会自动采集节目单（约 30 秒），随后打开 `http://127.0.0.1:8765/`。关闭窗口即停止服务。

**方式二：手动**

```bash
python tools/collect.py                    # 生成离线快照（首次必做；之后也可省略）
python tools/auto_segments.py --category 唱歌   # 可选：自动标注片段，启用「跳过空白」
python tools/serve.py                      # 启动（静态文件 + 播放代理 + 实时数据接口）
```

> 必须用 `tools/serve.py` 启动，不能用 `python -m http.server`：
> 浏览器无法直接播放 B 站的流（CDN 校验 Referer，网页伪造不了），
> 需要这个本机进程代取接口、代转媒体流。
> **回放清单与小路状态也都由它现场代取**，用 `http.server` 会失去「实时数据」能力。

然后浏览器访问 `http://127.0.0.1:8765/`。

> 页面本身是纯静态的。`data/programs.js` 只是网络异常时的兜底；
> 正常联网时，页面**每次打开都会重新抓一份最新的回放清单**（见「数据更新」）。

**需要联网**：视频流与弹幕由 B 站官方播放器提供，封面图取自 B 站图床。
**自动标注需要 `ffmpeg`**：它只在本机下载音频做分析，不影响页面本身的纯静态性质。

## 工作原理

### 1. 确定性虚拟频道时间轴（EPG）

```
position = ((now - epoch) + drift) mod cycleLength
```

- `epoch` 固定为 `2026-09-25T00:00:00+08:00`，`cycleLength` = 全部节目时长之和（111.7 小时）。
- 节目单由「固定种子 + 确定性洗牌」生成，是时间的**纯函数**，不依赖任何可变状态。
  服务端重启、页面刷新、多台设备打开，都会落到同一个位置 —— 这就是「随时打开都在直播中」。
- `drift` 只在用户点「播放某一场」时改变（进入单集播放模式），点「回到直播」归零。

### 2. 不重复的保证

- 一个循环内每个片段**只出现一次**，循环长度 111.7 小时 > 24 小时，
  因此**任意 24 小时内不会有任何一场重复**。
- 洗牌后有一道修复：相邻两个节目不允许同类型，避免连续三段闲聊。

### 3. 播放与弹幕

播放使用 B 站官方嵌入播放器，参数均经源码核实：

| 参数 | 作用 |
|---|---|
| `bvid` + `p` | 指定投稿与分P（61 个片段精确到分P） |
| `t` | 起始秒数，用于对齐「直播中」的进度 |
| `autoplay=1` | 自动播放（该播放器默认即为 true） |
| `muted=1` | 静音起播，以符合浏览器自动播放策略 |
| `danmaku` | 弹幕开关，默认开启 |

播放器是本站自己的 `<video>`（dash.js + MSE），**播放进度可以直接读取**：每秒的 `tick()`
从 `currentTime` 推算出当前时间轴位置，跨过单元边界就自动加载下一段，进度条也由它驱动。
不需要靠墙钟猜测，也不受跨域限制。

**默认静音**：播放器下方有「默认静音：开/关」按钮，选择会存进浏览器
（`localStorage` 键名 `xl_muted`），下次打开仍然生效。

- 「开」（默认）：静音起播，符合浏览器自动播放策略，打开页面即自动开始播放。
- 「关」：以带声音的方式起播。**浏览器可能拦截带声音的自动播放**，此时播放器会停在待播放状态，
  点一下播放器内的播放键即可。这是浏览器策略，不是本站可以绕过的。

> 说明：关闭默认静音后，若仍想临时静音，直接点播放器控制栏的音量键即可（我们无法从外部控制）。

### 4. 画质与 1080P

**结论：本站自带播放器，可在页内直接切换清晰度，最高 1080P。**

关键发现（这决定了整个取流方案）：

1. **MP4 通道封顶 720P，1080P 只在 DASH 通道里。** 调 `playurl` 时 `fnval=1`（MP4/durl）
   即使带登录也最多给到 720P；只有 `fnval=16`（DASH）才会下发 1080P（画质 id `112` / `80`）。
2. **DASH 的每条轨道就是一个 m4s 文件**，用 `SegmentBase`（`initialization` + `index_range`）
   描述索引。服务端据此生成一份 **isoff-on-demand 的 MPD**，交给页面里的 **dash.js + MSE** 播放。
3. **未登录时接口只下发低码率。** `accept_quality=[112,80,64,32,16]` 虽然五档齐全，
   但未登录时 `dash.video` 实际只返回 **480P(32) 与 360P(16)**。
4. **CDN 校验 Referer，且接口没有 CORS 头。** 不带 `Referer: https://www.bilibili.com` 会 403，
   浏览器也不能直连接口 —— 所以取流必须经由本站服务端代理。

因此正确做法是**在页内登录**（见下一节）：服务端拿到 `SESSDATA` 后即可取到 1080P 地址。

### 登录流程不会把你带走

点播放器右上角「登录」后：

1. 页内直接弹出**二维码**（`qrcode.min.js` 本地渲染），**不会跳转到 B 站**；
2. 页面轮询扫码状态，扫码确认后服务端从 `Set-Cookie` 取出 `SESSDATA` 存到本机
   `tools/sessdata.txt`，并把用户名回填到按钮上 —— 全程停留在本站页面；
3. 登录后播放器按新的登录态重新取流，画质菜单里就会出现 1080P 选项。

凭据只存在本机文件里，由服务端读取，**不写进页面、不上传任何地方**。

> 提示：1080P 能否取到取决于该账号的 VIP 状态。想换账号，删掉 `tools/sessdata.txt`
> 后重新扫码即可。

## 跳过空白片段（自动标注）

**能做什么**：开启后，播放器只播「有内容」的片段，片段之间的内容（闲聊、调设备、白板写字、离开座位）
会被自动跳过，到片段末尾自动跳到下一个片段起点。

### 数据来源：音频分析（自动）

不用手动标记。`tools/auto_segments.py` 会：

1. 按需从 B 站 CDN 取该分P 的**音频流**（67 kbps，按 10 分钟分块处理，不长期落盘）；
2. 用 ffmpeg 算出逐秒的**整体响度**与 **25–100Hz 相对能量**；
3. 两条判据各自做 **Otsu 自适应阈值**分割，**同时满足**才算「有内容」：
   - ① 整体够响 → 排除静音与低语
   - ② 25–100Hz 能量占比够高 → 说明有伴奏（贝斯/底鼓），**即在唱，而不是纯聊天**
4. 取持续够长的区段，间隔小于 `--min-gap`（默认 50 秒）的合并；
5. **超长段再切一刀**：有些场次全程垫着背景音乐，两条判据都不掉，会连成一大块
   （实测出现过 70 分钟的单段），所以给段长设上限 `--max-seg`（默认 720 秒），
   超出时在目标位置附近**能量最低处**切开（多半是换气或间奏）；
6. **歌曲边界精修（关键补充）**：只看音频会把歌从中间切开，所以还会用画面左上角的
   「已唱：…」浮层重建边界（见下一节）；
7. 输出 `data/segments.js`。

### 歌曲边界精修：读画面左上角的「已唱：…」浮层

**问题**：音频能判断「这一秒在不在唱」，但**分不清「一首歌结束」与「歌内间奏」**——
两者都是伴奏短暂减弱。实测「戒烟」（真值约 557–1012 秒）这一首，
伴奏判据在歌内部给出了 **18 个**「进/出」点：

```
进：556 608 627 694 752 830 873 899 955 990
出：583 615 669 865 902 946 972 1003
```

用它当切点，戒烟必然被从中间劈开。旧结果确实如此：`578–923` + `957–1166`，
戒烟（557–1012）在 957 处被切断 —— 这就是「歌头歌尾被切掉」的真实形态。

**解法**：主播把歌名以固定样式打在**画面左上角**（`已唱：<歌名列表>`），
**每开始唱一首新歌就往列表里加一个名字**。这个浮层的像素变化与歌曲起点一一对应，
而且不需要 OCR —— 逐帧做区域差分即可。

裁切区域（相对坐标，抗分辨率变化）：

```
crop=iw*0.26:ih*0.045:0:ih*0.008      # 852x480 下约 x 0~210, y 5~22
```

**为什么必须选左上角**：同一套方法用在画面中部偏右（那是**歌词**，每句都变）会给出
37~51 个假峰；左上角「已唱」列表的信噪比则是决定性的：

| 抽帧步长 | 帧数 | 背景（p50~p95） | 非零帧数 |
|---|---|---|---|
| 5 秒 | 1447 | **0.0000** | 39 |
| 1 秒 | 125 | **0.0000** | **1**（t=566，登记「戒烟」） |
| 1 秒 | 130 | **0.0000** | **1**（t=998，登记下一首） |

**峰值语义**：峰值出现在歌名被写进列表的时刻，也就是**这首歌的起点**
（实测 t=300 的浮层是「已唱：不开灯俱乐部」，t=565 变成「已唱：戒烟、不开灯俱乐部」，
而真值戒烟约在 557 秒开始）。所以峰值天然是**相邻两首歌的切分点**。

**做法：以峰值为骨架重建分段，而不是往音频段里插补丁。**
只要音频那条假边界还在，歌就仍会被切断，所以必须整体替换：

- 相邻两个峰值之间 = 一首歌，直接成为一段；
- 峰值本身多落在「主播报幕 / 静音」处（实测 t=570 是 −38.9 dB、t=3490 是 −71.1 dB），
  切在那里不会伤到任何一首歌；
- 间隔不足 `--min-seg` 的峰值判为误检并合并（实测 5875 / 5895 相隔 20 秒，是同一首被登记两次）；
- 间隔超过 `--max-seg` 的区间（实测 1595→3035 长达 24 分钟）必然有未登记的内容，
  用音频结果在内部兜底细分；
- 首个峰值之前、末个峰值之后同理交给音频兜底。

**效果**（cid 42117366217）：

| | 戒烟所在段 | 是否被切断 |
|---|---|---|
| 旧（纯音频） | 578–923 ＋ 957–1166 | **是**，957 处劈开 |
| 新（已唱骨架） | **570–1000**（一整段） | 否 |

**取舍**：默认 5 秒步长抽帧，落点偏差 ≤ 5 秒 —— 对「跳转到某首歌」完全够用
（不会有人在意少跳了 5 秒前奏）；抽一整支 2 小时视频约 25 秒，成本可接受。
用 `--no-sung` 可关闭这一步，退回纯音频流程（旧行为）。

### 为什么 25–100Hz 是关键判据

人声基频在 100Hz 以上，而伴奏的贝斯与底鼓集中在 25–100Hz。所以这一段的相对能量
就是「有没有伴奏」的代理指标。实测同一段音频：

| 状态 | 整体响度 | 25–100Hz 相对能量 |
|---|---|---|
| 有伴奏（在唱） | −24 ~ −28 dB | **−2.7 ~ −11 dB** |
| 纯说话 | −34 ~ −50 dB | **−18 ~ −35 dB** |

区分度很大。只看响度的话，「大声聊天」会被误判成唱歌；加上这条判据就能分开。

**参数是按实测间隔定的**：歌内低谷（换气、间奏）约 27–34 秒，歌间聊天间隔在 83 秒以上，
所以 `--min-gap` 取 50 秒正好把两者分开。

**效果对比**（同一场 2 小时的分P）：

| | 只看响度（旧） | 响度 + 伴奏（新） |
|---|---|---|
| 段数（同一分P） | 17 | 19 |
| 最长段 | **41.1 分钟** | 13.8 分钟 |
| 段长中位 | — | **3.8 分钟（≈ 一首歌）** |
| 判定为有内容 | 106 分钟 | 79 分钟 |

全部 **61 个分P 都已完成自动分段**，合计 **851 段**，段长中位 3.4 分钟、均值 4.6 分钟、
最长 14.0 分钟，覆盖 **64.6 小时**。其中 9 个唱歌分P 136 段（段长中位 3.8 分钟，≈ 一首歌），
其余 52 个分P 715 段。开启「跳过空白」后的循环长度由 111.7 小时降到 **64.6 小时**。

**用已知答案验证过**（cid 42117366217，人工读帧的真值：戒烟约 557–1012 秒）：

| | 戒烟所在段 | 结论 |
|---|---|---|
| 旧（纯音频） | 578–923 ＋ 957–1166 | ❌ 在 957 处把歌劈成两半 |
| 新（已唱骨架） | **570–1000**（一整段） | ✅ 完整包含，且边界落在歌与歌之间 |



在转向画面与音频之前，我把所有可能的数据源都核查过了：

| 数据源 | 核查结果 |
|---|---|
| 官方章节 `viewPoints` | ❌ 这些回放没有章节（`view_points = None`；wbi 接口被风控挡回 HTML） |
| 高能进度条 `bvc.bilivideo.com/pbp/data` | ❌ 已废弃，返回 404 |
| 弹幕时间轴 | ❌ 未登录只拿到 2.9% 的弹幕（1415 / 48490）；wbi 签名后条数完全一致，且文本只有反应与点歌请求 |
| 视频简介 | ❌ 全部为空 |
| 画面中部偏右（歌词） | ❌ 每句都变，37~51 个假峰 |
| 音频响度 | ✅ 可行，用作「有没有内容」的判据（已采用） |
| **画面左上角「已唱：…」浮层** | ✅ **可行，用作歌曲边界（已采用）** |

### 怎么用

```bash
python tools/auto_segments.py --category 唱歌     # 推荐：只处理唱歌类
python tools/auto_segments.py --bvid BV16RuU6AEvc # 单个投稿
python tools/auto_segments.py --all               # 全部 42 个 / 61 个分P / 约 112 小时音频
python tools/auto_segments.py --bvid BVxxx --no-sung   # 只用音频，不抽帧读「已唱」
```

需要 `ffmpeg`（脚本会自动在 PATH 与常见目录中查找，也可用 `--ffmpeg` 指定）。
已分析过的分P 结果缓存在 `tools/.cache/auto_seg.json`，重跑会跳过。
生成后回到页面点「**跳过空白：开**」即可。

**两层缓存，重跑成本很低**：

| 缓存 | 内容 | 作用 |
| --- | --- | --- |
| `tools/.feat/` | 每 600 秒一块的逐秒音频特征 | 唯一需要下载音频的环节；只要它还在，改参数/重跑都只花几分钟 |
| `tools/.cache/auto_seg.json` | 最终分段结果 | 命中则整块跳过 |

实测：抽 120 秒音频特征约 1.7 秒 → 单块 600 秒约 8.5 秒 → **全部 61 个分P 约 0.3 小时**
（前提是 `.feat/` 有缓存）。首次全量跑没有缓存时才是整段下载时间。

> **升级后需要重跑**：缓存键带流程版本标记（当前 `s2`）。改动判据或边界算法后，
> 请把 `CACHE_VERSION` 递增，旧缓存会被忽略并保留在文件里，未重跑的分P 继续沿用旧结果
> （写 `segments.js` 时按「新版本优先、旧版本兜底」合并），实现渐进升级而不丢数据。

> **边界精修需要 `numpy` + `pillow`**：缺依赖时脚本会提示
> `pip install numpy pillow` 并自动退回纯音频流程，不会中断。用系统 Python 直接双击
> `启动.bat` 时**不需要**这两个包（网页服务只用标准库）。

### 手工修正（可选）

自动结果是启发式的，个别不准时可以在页面里改：播放器右上角「**标注**」→
播放到片段开头按 `M`、结尾再按 `M` → 面板底部生成 JSON → 覆盖 `data/segments.js`。
标注存在浏览器 `localStorage`，支持「撤销上一个 / 清空本分P」。
打开标注模式会**自动关掉「跳过空白」**，避免在已裁剪的片段里重复标注。

### 数据格式（`data/segments.js`）

以 **cid** 为键（不是 BV 号——一个投稿可能拆成多个分P，每个分P 有独立 cid）：

```js
window.SEGMENTS = {
  "40755528179": [
    { "start": 191, "end": 432, "label": "" }
  ]
};
```

`start` / `end` 是**该分P 内的秒数**。超出分P 时长的部分会被自动裁掉，非法项会被丢弃。
**没标注的分P 会整段照常播放**，不会被跳过。

### 跳转的代价（实测）

跳转落点**精确到 0.01 秒内**，耗时约 1.4~2.1 秒（含 seek 后的重新缓冲）：

| 目标 | 落点 | 耗时 |
|---|---|---|
| 同分P，t=1508s | 1508.00s | 2139 ms |
| 跨分P，t=1028s | 1028.00s | 1424 ms |

（早期版本用 B 站 iframe 时只能靠重载换 `t=` 参数，机制与那组数据都已作废。）

### 验证记录

开启后时间轴循环长度 111.7h → **64.6h**（差值等于「整段 − 全部标注片段」）；
跳到已标注的那一场时，进度条时长显示的是**该片段长度**而非整段，信息卡显示片段标签；
关闭后恢复整段时长。

## 分段导航（跳转到想看的片段）

自动标注出的分段不只是用来「跳过」，也可以**直接点着跳**。

### 两个入口

| 位置 | 内容 |
|---|---|
| 播放器右上角「**分段**」 | 展开本场分段列表，点任意一段即跳到该段起点 |
| **剧场模式下的左右竖条** | 左侧竖条＝本场分段（当前段红色高亮、已播过的变暗）；右侧竖条＝接下来播什么（标题＋开播时间），点击即切过去 |

剧场模式的三列布局是「左竖条 200px ｜ 播放器 ｜ 右竖条 200px」。
实测 1600×900 下播放器为 **1120×630**（16:9，比例 1.778）。
窗口宽度不足 1280px 时会自动收起竖条，优先保证画面。

### 跳转是怎么实现的

播放器是本站自己的 `<video>`（dash.js + MSE），跳转分两种情况：

| 情况 | 做法 |
|---|---|
| **同一分P 内** | 直接把 `currentTime` 设到段内偏移，不重新取流 |
| **跨分P** | 重算漂移量 `drift = (目标段起点 + 段内偏移) - (now - epoch) mod cycleLength` 并重新取流加载 |

实测两次向后大跨度跳转，**落点都精确到 0.01 秒内**：

| 目标 | 落点 | 耗时 |
|---|---|---|
| 同分P，t=1508s | 1508.00s | 2139 ms |
| 跨分P，t=1028s | 1028.00s | 1424 ms |

耗时主要来自 seek 之后的重新缓冲，两次相当，与是否跨分P 无直接关系。
同一套逻辑在两种模式下都成立：

- **「跳过空白」开启**：时间轴单元就是分段本身，点击即跳到该单元起点；
- **「跳过空白」关闭**：单元是整个分P，点击即跳到分P 内的那个时间点。

当前所在段的高亮由自己的时钟推算（每跨过一段边界只更新高亮，不重载播放器）。

### 关于「歌曲名」

**歌名在画面里，不在接口里。** 抽帧读画面后确认，主播会用两种浮层之一显示当前唱的内容：

| 浮层 | 说明 | 出现在 |
|---|---|---|
| **「歌名 - 歌手」字幕** | 如 `不开灯俱乐部 - YELLOW黄宣`、`戒烟 - 李荣浩` | 部分歌曲（不是每首都显示） |
| **整场歌单列表** | 编号列表，随进度缓慢滚动 | 少数直播 |

所以标签的获取方式是**抽帧读画面**：

```bash
python tools/setlist_frames.py --bvid BV1jshn6vEik --by-segments   # 按每个分段起点采样
```

产物在 `tools/.setlist/`（每 6 帧竖排一张，便于读字幕/歌词条带）。
读出后写进两个文件，页面会自动显示：

| 文件 | 用途 | 显示位置 |
|---|---|---|
| `data/labels.js` | **分段内容标签**（歌名 / 歌词首句 / 内容类型） | 分段列表每行右侧，悬停显示歌手或歌词提示 |
| `data/setlists.js` | 整场歌单（按演唱顺序） | 分段列表上方的「本场歌单」区块 |

`data/labels.js` 用「起始秒数」作键，所以重跑 `auto_segments.py` 后只要段落起点不变，标签仍然有效：

```js
window.SEGLABELS = {
  "42117366217": { "242": { "label": "不开灯俱乐部", "sub": "YELLOW黄宣" } }
};
```

**识别优先级（三级，保证不出现空白）**：

1. **歌名字幕** → 直接用作标签（如 `戒烟`、`死ぬのがいいわ`、`Bibbidi-Bobbidi-Boo`）；
2. **当屏歌词** → 取歌词首句作内容提示（如 `美丽的泡沫 虽然一刹那花火`、`It's cruel summer`）；
3. **无画面文字时按分类兜底** —— **不使用「演唱」这类模糊标注**：每行都一样等于没标。
   - **歌曲类场次（唱歌 / 电台）**：按段长估算 `约 N 首`（约 3.8 分钟一首），
     悬停说明「该场画面未显示歌名或歌词，此处按段长估算」；
   - **其余场次（游戏 / 杂谈 / 联动 / 特别回 / 其他）**：本来就没有歌，估算「几首」毫无意义，
     改用 `第 N 段` 按序号定位，悬停说明「该场画面未显示文字信息，此处按段落定位」。

当前实测（851 段）：**54 段**读到具体歌名或歌词，**797 段**按段长或序号定位，**0 段**为模糊的「演唱」。
每段的**起止时间与时长**都放在悬停提示里。

除歌名外，画面文字还能识别出内容类型，例如某场的
`真心话投稿朗读`、`提问箱：关于学歌和游戏`、`提问箱：进 VR 的契机`。

**必须知道的限制**：

1. **有的场次画面上什么都没有。** 实测「只是在唱歌+ 2026-08-16」这一场全程不显示歌词或字幕，
   这种场次拿不到任何内容信息——这是数据源的硬限制，不是没努力。这类场次只能用段长估算，
   并可通过 `data/setlists.js` 补上整场歌单（该场的滚动歌单已补入部分曲目）。
   读取依赖视觉能力，只能逐场推进（已完成 5 个唱歌分P 的分段标签；自动分段本身 61/61 个分P 全部完成）。
2. **覆盖需要逐场读取。** 读取依赖视觉能力，无法纯脚本自动化；每场 17~25 段大约需要 3~5 张拼图。
3. **整场歌单只有顺序、没有时间点。** 歌单浮层是缓慢滚动的装饰性列表，不指示「当前唱到第几首」；
   强行按顺序映射会标错歌名，所以没有做。

## 自研播放器与清晰度

回放台用的是**自己的播放器**（原生 `<video>` + MSE），不是 B 站的嵌入播放器。

### 关键结论：1080P 只在 DASH 通道

实测（已登录大会员）同一分P：

| 通道 | 可用清晰度 |
|---|---|
| MP4（`fnval=1`，durl） | **只有 720P / 360P** —— 即便大会员也一样 |
| **DASH（`fnval=16`）** | **1080P 高码率 / 1080P 高清 / 720P / 480P / 360P** |

所以早期版本"登录了也没有 1080P"不是登录没生效，而是**走错了通道**。

### 实现

B 站的 DASH 轨道是「单个 m4s 文件 + `SegmentBase` 索引」（`initialization` + `index_range`），
所以服务端可以**直接生成 isoff-on-demand 风格的 MPD**，交给 dash.js 用 MSE 播放：

```
浏览器 <video> ← MSE ← dash.js
   └─ /api/dash?bvid=&cid=&qn=   服务端生成 MPD（BaseURL 指向本机代理）
   └─ /api/dashinfo?bvid=&cid=   返回该分P 的 DASH 清晰度阶梯
   └─ /api/stream?u=…            按字节范围转发 m4s（注入 Referer）
```

- 选轨优先 H.264（`codecid=7`），兼容性最好；音频取最高码率。
- **服务端缓存 90 分钟**：同一分P 只打一次 B 站接口，既省请求又避开风控（实测连续调用会 412）。
- DASH 初始化失败会**自动退回 MP4 通道**（此时最高 720P，并在信息卡说明）。

### 登录（全程在回放台内完成）

点播放器右上角「**登录**」→ 面板出现二维码 → 用 **B 站手机 App 扫码** → 确认。
登录成功后会自动按新清晰度重新加载。

- 登录信息只写入本机 `tools/sessdata.txt`，**只发给 B 站自己的接口**，不经任何第三方；
- 不收集、不上传账号信息；点「退出登录」即清除。

### 已知取舍

自研播放器**没有官方弹幕层**，所以本页不显示弹幕。
官方嵌入播放器有弹幕，但它没有清晰度参数、也无法页内控制——两者不可兼得。

## 数据更新

### 页面每次打开都取最新数据（默认行为）

**页面加载时会重新抓一份回放清单，不需要重跑任何脚本。** 打开页面 → 前端请求
`/api/programs?refresh=1` → `serve.py` 现场拉系列投稿 + 逐视频详情 → 返回与
`data/programs.json` **同构**（字段、排序、评分全部一致）的结果。

- 服务端用 8 路并发取详情，`42 个投稿 + 61 个分P` 实测约 **1.1 秒**；
- 页面顶部信息栏会显示数据来源，实时抓取时注明「**实时数据 HH:MM**」，
  回退到本地快照时显示「快照于 MM-DD HH:MM」；
- 抓取失败（离线、风控）时**自动回退**到 `data/programs.js` / `data/programs.json`，
  页面不会白屏 —— 所以这三个来源是「实时 → 内嵌 → 静态文件」的降级链。

> 代价：每次打开页面都会请求 B 站接口。已做 4 分钟内的**并发去重**（同一时刻多个
> 请求只触发一次抓取）与失败回退，但 `refresh=1` 本身不受 TTL 限制 —— 这是
> 「数据必须是用户打开网页时重新获取的新信息」这条需求的直接实现。

### 仍然可以手动重跑采集（离线快照）

```bash
python tools/collect.py            # 增量：已有缓存直接复用
python tools/collect.py --refresh  # 忽略缓存，全部重新采集
```

建议偶尔跑一次，让内嵌的 `data/programs.js` 保持较新 —— 它是网络异常时的兜底。

## 小路状态（右下角悬浮面板）

页面右下角有一个常驻的「**小路状态**」悬浮按钮，点击展开面板，可以看到：

### 数据接口

```
GET /api/status-board     小路状态（开播情况 + 最新投稿）
```

**这个接口不设有效缓存 —— 每次调用都重新问一次 B 站**，符合「数据必须是用户
打开网页时重新获取的新信息」的要求。`STATUS_LOCK` 只用来串行化写操作，不返回旧值。

开播状态走的是：

```
https://api.live.bilibili.com/room/v1/Room/get_status_info_by_uids?uids[]=<mid>
```

这条接口**不需要登录、不需要 wbi 签名、对 Referer 不敏感**，返回 `live_status`、
`title`、`room_id`、`cover_from_user`、`area_v2_name`、`face`、`online`、`live_time`。
真实房间号是 **1700301235**（不是空间里的短号）。

源码见 `tools/serve.py` 的 `fetch_live()` / `api_status_board()`。

### 为什么「动态」不能在服务端抓

主播的新动态（发帖）本该由服务端取，但**所有动态接口都已被风控挡住**，实测：

| 接口 | 结果 |
|---|---|
| `x/polymer/web-dynamic/v1/feed/space` | ❌ 412 |
| `x/space/dynamic/v1/feed/space` | ❌ 404 |
| `api.vc.bilibili.com/dynamic_svr/...` | ❌ 404 |
| `x/space/arc/search` | ❌ −799 |

所以在「最新回放」之外，面板只提供**跳转到动态页的链接**，不尝试在站内解析动态内容。
「新动态」的提示用「最新投稿有更新」来近似 —— 这是本机代理能做到的极限，
不做任何需要登录态或规避风控的尝试。

- 面板展开时才请求数据（`loadStatus(true)`）；收起时标记「已读」，小红点消失。

## 故障排查：二维码 Failed to fetch / 播放卡死

这两个症状**同一个原因**：页面没有连上本机服务，所以 `/api/*` 根本不存在。
本页启动时会自检一次；连不上就不再取流，并把原因直接写在画面上。

正确启动方式（二选一）：

1. 双击项目里的 `启动.bat`；
2. 或命令行 `python tools/serve.py`，然后访问 `http://127.0.0.1:8765/`。

**不要**直接双击 `index.html`（`file://` 下没有 `/api`），也不要只看静态预览。

| 现象 | 原因 |
|---|---|
| 「本机服务没有连上」横幅 | `serve.py` 没运行，或访问的是静态预览 |
| 提示「端口 8765 已被占用」 | 通常已有一个实例在跑，直接开 `http://127.0.0.1:8765/` 即可；要换端口用 `--port 9000` |
| 播放中断后提示「正在重新取流」 | 播放地址有 2 小时时效，会自动重取一次 |
| 改了 `tools/serve.py` 后新接口 404 | 服务进程不会热加载代码，必须重启 |

## 已知限制

1. **暂停会漂移**：频道时钟独立于播放器运行，用户暂停后进度会与「直播中」错开。点「回到直播」复位。
2. **播放器 UI 不可定制**：播放器为跨域 iframe，无法自定义控制栏。
3. **切弹幕 / 开声音会重载**：跨域无法动态控制，需重载 iframe；重载时会按 EPG 重算偏移，进度不会跳回开头。
4. **1080P 取决于你自己的 B 站登录状态**：未登录时播放器只能给到较低清晰度，登录后自动可用 1080P。
   **本项目不接触、不存储任何账号凭据。**
5. **自动播放能否真正开始，取决于浏览器策略**：参数本身已验证正确（静音时传 `muted=1`、
   关闭默认静音后传 `muted=0`），但浏览器是否允许起播属策略问题，无头环境无法代表真实浏览器。
   若打开页面没有自动开始，点一下「进入直播」即可。
6. **分类为自动打标**，存在少量误差。当前有 1 条归入「其他」，需人工确认（见下）。
7. **「跳过空白」的片段是音频启发式检测的**：对唱歌类场次准确度较高（实测与弹幕线索仅差 6 秒），
   但闲聊/游戏场次没有明显响度落差，检测结果会接近整段（等于不跳过，属安全行为）。
   个别不准时可用页面「标注」手工修正。未标注的分P 会整段播放。
8. **`data/segments.js` 的覆盖是渐进的**：只有跑过的分P 才有片段表。没跑过的分P
   会整段播放（**不会有任何报错提示**），这是有意为之——宁可整段播，也不要切错。
   想看当前覆盖情况：`python tools/verify_segments.py`（会列出 cid 数与段数）。

## 分段覆盖情况（怎么自查）

```bash
python tools/verify_segments.py
```

输出形如：

```
segments.js：N 个 cid，M 段
cid 42117366217（19 段）
  ✅「戒烟」完整落在段 570–1000 内（真值 557–1012，容差 20s）
全部通过
```

`verify_segments.py` 里内置了几首**已知真值**的歌曲（目前是「戒烟」557–1012 秒），
用来防止「改算法把歌切两半」这类回归。容差 20 秒是因为抽帧步长是 5 秒，
人耳真值本身也有 ±20 秒的模糊度。

**没有任何 cid 被静默漏掉**是这条流水线的硬要求：`main()` 写 `segments.js` 时按
「当前版本优先、旧版本兜底」合并，所以渐进重跑不会让已覆盖的 cid 掉出去。
